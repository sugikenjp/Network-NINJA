# Network-NINJA

[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

**未使用のネットワーク空間を「Active Trap Zone」に。意図的なネットワーク設計によって、ルーティングそのものを検知面に変えます。**

Network-NINJA は、企業ネットワーク内部の想定外の通信を検知する、オープンソースの分散型検知システムです。軽量なセンサーがルーターや L3 スイッチ上でコンテナとして直接動作し、集中管理用の Manager がイベントの収集と設定管理を行います。

Network-NINJA は次の要素を組み合わせています。

- 既存のルーターおよび L3 スイッチ
- 意図的なルーティング設計
- ネットワーク機器または Linux ホスト上で動作する軽量な分散センサー
- 集中的な設定管理と監視

Network-NINJA 自体は、ルーティングの設定や制御を行いません。

ネットワーク管理者は、正規の通信が想定されないネットワークレンジを **Active Trap Zone** として定義し、既存のルーティング基盤を設定して、そのレンジ宛ての通信を Network-NINJA センサーへ誘導します。センサーは選択された通信を観測し、検知イベントを Network-NINJA Manager に送信します。

このアプローチにより、セキュリティ監視をネットワーク設計プロセスの一部として組み込むことができます。

> Network-NINJA はネットワーク設計を置き換えるものではありません。
> 組織が自らのネットワークを深く理解し、セキュリティを設計に組み込むことを促すためのものです。

## 概要

多くの組織は、本社、データセンター、支店、店舗などにまたがる、大規模でセグメント化されたネットワークを運用しています。

その中には実際に使われているレンジもあれば、未使用、予約済み、あるいは通常の業務通信から意図的に除外されているレンジもあります。

こうしたレンジに向かう通信は、セキュリティ上の有力なシグナルになり得ます。たとえば次のような事象と関連している可能性があります。

- ネットワーク偵察
- 内部ネットワークのスキャン
- 設定ミス
- 不正アクセスの試み
- マルウェアの活動
- 不審なラテラルムーブメント

Network-NINJA を使うと、各拠点にすでにあるネットワーク機器の上に軽量センサーを配置し、それらのセンサーが何を監視するかを一元的に管理できます。

```
      Enterprise Network
              |
              v
     Router / L3 Switch
              |
     Routing configured
    by network operators
              |
              v
    Network-NINJA Agent
        Network Sensor
              |
     Detection via Syslog
              |
              v
   Network-NINJA Manager
              |
  +-----------+-----------+
  |                       |
Web UI                  SQLite
```

## コアコンセプト: Active Trap Zone

Network-NINJA の基本的な考え方はシンプルです。

> **正規の通信が想定されないネットワークに向かう通信は、注意に値する。**

**Active Trap Zone** とは、次の条件を満たすネットワークレンジです。

- 正規の業務通信に使われていない
- ネットワーク内を探索する侵入者が調べたくなる程度に、もっともらしく見える
- 既存のネットワーク基盤のルーティングによって、近くの Network-NINJA センサーへ誘導されている

従来のハニーポットとは異なり、罠は単一のおとりホストではありません。罠は **アドレスの選定、トポロジー、ルーティング、センサーの配置** によって構成されます。そのため、検知は一つのシステムに集中せず、ネットワークアーキテクチャ全体に分散します。

効果的な Active Trap Zone を設計するには、侵入者が次にどこを探るかを予測する必要があります。防御側はどの宛先をもっともらしく見せるかを決め、侵入者はどこを探索するかを決めます。Network-NINJA は、この駆け引きを観測可能にします。

```
1. もっともらしく見える未使用レンジを Active Trap Zone として選定
                         |
                         v
2. 必要なルーティングを設計
                         |
                         v
3. ルーターまたは L3 スイッチを設定
                         |
                         v
4. Zone 宛ての通信を Network-NINJA Agent へ誘導
                         |
                         v
5. 選択したプロトコルとポートを監視
                         |
                         v
6. 検知イベントを生成・収集
```

## 既存アプローチとの関係

未使用アドレス空間の監視自体は新しい手法ではありません。インターネット規模のダークネットやネットワークテレスコープは、以前からこの手法でスキャン活動を観測してきました。

Network-NINJA は、この考え方を企業ネットワークの内部に持ち込み、設計の方法論へと発展させます。

- Active Trap Zone は、内部ネットワークを探索する侵入者にとってもっともらしく見えるよう選定します。
- センサーは、各拠点にすでに導入されているルーターやスイッチ上でコンテナとして動作します。
- すべてのセンサーは、単一の Manager から一元管理されます。

Network-NINJA は IDS、NDR、ハニーポット、デセプション製品を置き換えることを目的としていません。ネットワーク設計から得られる、早期かつ低コストなシグナルによってそれらを補完します。

## Security by Design

Network-NINJA は、ネットワーク設計と通信の検知を意図的に分離しています。

### ルーティングはネットワーク基盤が担う

どの通信が各 Network-NINJA Agent に届くかは、既存のルーターや L3 スイッチが決定します。

Network-NINJA が自動的にルートを投入したり、ルーティングテーブルを変更したりすることはありません。

### センシングは Network-NINJA が担う

Network-NINJA Agent は、届いた通信を観測し、条件に一致するイベントを報告します。

### 検知面は管理者が設計する

管理者は次の事項を決定します。

- どのネットワークレンジを Active Trap Zone とするか
- どのレンジが正規の通信を受けるべきでないか
- センサーをどこに配置するか
- 各センサーへ通信をどのようにルーティングするか
- 各センサーでどのプロトコルとポートを監視するか
- どの通信を監視対象から除外するか

このプロセスには、組織の次の事項に関する理解が必要です。

- ネットワークトポロジー
- アドレス割り当て
- ルーティングアーキテクチャ
- セグメンテーション
- 通常の通信経路
- 想定される運用通信

そのため、Network-NINJA は単なるネットワークセンサーではありません。設計段階からセキュリティ監視をネットワークアーキテクチャに組み込むためのアプローチです。

```
Network Understanding
         +
Routing Design
         +
Distributed Sensors
         +
Centralized Management
         =
Security by Design
```

## アーキテクチャ

Network-NINJA は主に、**Manager** と 1 台以上の **Agent** で構成されます。

```
              +-----------------------+
              | Network-NINJA Manager |
              +-----------+-----------+
                          |
               Management and Control
                          |
         +----------------+----------------+
         |                                 |
         v                                 v
+-----------------+               +-----------------+
|     Agent A     |               |     Agent B     |
| Network Sensor  |               | Network Sensor  |
+--------+--------+               +--------+--------+
         ^                                 ^
         |                                 |
  Router / L3 Switch                Router / L3 Switch
         ^                                 ^
         |                                 |
  Active Trap Zone                  Active Trap Zone
      Traffic                           Traffic
```

Manager が集中管理を担い、Agent は分散ネットワークセンサーとして動作します。

Active Trap Zone の通信を各 Agent へ届けるためのルーティングは、組織のルーターや L3 スイッチ側で別途設定します。

## コンポーネント

### Manager

Network-NINJA Manager は、集中的な可視化と設定管理を提供します。

現在の Manager の機能は次のとおりです。

- Web ベースの管理画面
- REST API
- Agent のハートビート管理
- ノードの状態監視
- Syslog の受信
- Syslog の検索と取得
- 設定の配信
- SQLite によるデータ永続化

Manager は、デフォルトで次のポートで待ち受けます。

| サービス        | デフォルトポート |
| --------------- | ---------------- |
| Web UI          | TCP/8080         |
| REST API        | TCP/8080         |
| Syslog 受信     | UDP/514          |

Manager に UDP/514 へバインドする権限がない場合は、UDP/5514 などの非特権ポートを使用できます。

### Agent

Network-NINJA Agent は、軽量な分散ネットワークセンサーです。

各 Agent は次の処理を行います。

- 選択されたネットワーク通信を監視
- Syslog で検知イベントを送信
- Manager へハートビートを送信
- Manager に設定の更新を問い合わせ
- 一元配信された監視設定を適用
- 自身のノード ID と表示ラベルを報告

Agent はコンテナとして動作し、対応ネットワーク機器([動作確認済みプラットフォーム](#動作確認済みプラットフォーム) を参照)、サーバー、仮想マシン、その他の適切な Linux 環境に導入できます。

### ルーターまたは L3 スイッチ

ルーターや L3 スイッチは、Network-NINJA のソフトウェアには含まれません。

これらは引き続き企業ネットワーク内のルーティングを担います。ネットワーク管理者は、各 Active Trap Zone 宛ての通信を Network-NINJA Agent へ誘導するよう設定します。

```
社内ネットワーク:      10.0.0.0/8
使用中のレンジ:        10.1.0.0/16 - 10.20.0.0/16
Active Trap Zone:      10.200.0.0/16 (未使用だが、サーバーセグメントに見える)
誘導先センサー:        Network-NINJA Agent
```

これは概念的な例です。ルーティング設定は、実際のネットワーク環境に合わせて設計する必要があります。

## 通信の監視

Network-NINJA Agent は、Manager から受け取った設定に基づいて、選択された通信を監視します。

現在対応している通信の種類は次のとおりです。

- ICMP Echo Request
- ICMP Echo Reply
- TCP 80 番ポート(主に HTTP)
- TCP 443 番ポート(主に HTTPS)
- TCP 445 番ポート(主に SMB)

複数の種類が有効な場合、Agent はそれらを組み合わせてパケットキャプチャフィルターを生成します。概念的な例は次のとおりです。

```
ICMP Echo Request or Reply
or TCP port 80
or TCP port 443
or TCP port 445
```

これらのプロトコルとポートは、次のような活動の可視化に役立ちます。

- ネットワーク偵察
- 許可されていないサービス探索
- 想定外のアクセス試行
- マルウェアの活動
- ラテラルムーブメント
- 設定ミスによる通信

Network-NINJA は、プロトコルやポート番号だけで通信を悪意あるものと判定することはありません。たとえば TCP 80 番や 443 番は、正規の通信でも広く使われています。

セキュリティ上の価値は、次の要素の組み合わせから生まれます。

- 通信がどこで観測されたか
- 正規の通信が想定されていたか
- どの送信元が通信を発生させたか
- どの Active Trap Zone にアクセスがあったか
- どのプロトコルやポートが使われたか
- 周辺の運用状況

そのため、意図的に設計された Active Trap Zone に届いた通信は、ポート番号単体よりもはるかに強いシグナルになります。

## 検知シナリオの例

ある組織が、主に次のプライベートアドレス空間を使用しているとします。

```
10.0.0.0/8
```

この組織は、侵入者がサーバーの存在を期待しそうな未使用レンジを選んで Active Trap Zone に指定し、近くの Network-NINJA Agent へ向かうルートを設定します。

```
Workstation or compromised host
              |
              | Reconnaissance traffic
              v
       Router / L3 Switch
              |
              | Administrator-defined route
              | for the Active Trap Zone
              v
     Network-NINJA Agent
              |
              | Matching traffic detected
              v
          Syslog event
              |
              v
     Network-NINJA Manager
```

あるホストが偵察を行い、Active Trap Zone に向けて ICMP、HTTP、HTTPS、SMB の通信を送信すると、Agent は条件に一致する通信を観測し、送信元、検知したセンサー、対象レンジを含むイベントを生成します。

## 遮断ではなく検知

Network-NINJA は検知と可視化に焦点を当てています。

次の用途を想定した設計ではありません。

- ファイアウォール
- 侵入防止システム(IPS)
- アクセス制御の代替
- ルーティングの自動制御
- マルウェア分類エンジン

Network-NINJA は選択された通信を観測し、防御側が調査するための情報を提供します。

遮断、隔離、復旧、インシデント対応は、組織の既存のセキュリティ対策やネットワーク制御で行ってください。

## 分散配置

Network-NINJA は、次のような複数のネットワーク拠点を持つ環境を想定して設計されています。

- 本社
- データセンター
- 支店
- 店舗
- リモート拠点
- ネットワーク集約ポイント

Agent はルーターや L3 スイッチ上で直接動作できるため、専用の監視アプライアンスを置かずに各拠点へセンサーを配置できます。

```
           +-----------------------+
           | Network-NINJA Manager |
           +-----------+-----------+
                       |
     +-----------------+-----------------+
     |                 |                 |
     v                 v                 v
HQ Agent          Branch Agent       Store Agent
     ^                 ^                 ^
     |                 |                 |
  HQ Router        Branch Router      Store Router
```

Agent は定期的に Manager へ状態を報告するため、分散したセンサーを一元的に監視できます。

## 機能

### 実装済みの機能

- Manager と Agent による分散アーキテクチャ
- マルチベンダーのネットワーク機器で動作確認済みのコンテナ型 Agent
- 設定可能なパケット監視
- ICMP Echo Request / Reply の監視
- TCP/80、TCP/443、TCP/445 の監視
- Syslog によるイベント転送
- Syslog の集中受信と保存
- Agent のハートビート監視
- ノードのオンライン/オフライン状態
- 設定の一元配信
- Agent による定期的な設定の問い合わせ
- REST API
- Web ベースの管理画面
- SQLite による永続化
- Docker による導入
- ホストネットワークおよび macvlan による導入オプション

### 設計原則

- 早期に検知する: 防御だけでは十分ではない
- すべてをミラーするのではなく、重要な通信をルーティングする
- ネットワークアーキテクチャそのものを罠の一部にする
- ネットワークの知識を防御能力に変える
- 通信を流すためだけでなく、攻撃者を検知するためにネットワークを設計する
- ルーティングとセンシングの責任分離
- 遮断ではなく検知

## Agent の起動

以下は Docker が動作する Linux ホストでの導入手順です。ネットワーク機器へ導入する場合は、各機器のコンテナ機能のドキュメントと [動作確認済みプラットフォーム](#動作確認済みプラットフォーム) を参照してください。

### 1. コンテナイメージのビルド

```
cd agent
docker build -t ninja-agent .
```

### 2. Agent の起動

```
docker run -d \
  --name ninja-agent \
  --restart unless-stopped \
  --cap-add=NET_RAW \
  --cap-add=NET_ADMIN \
  --network=host \
  -e MANAGER_URL="http://192.168.1.100:8080" \
  -e SYSLOG_SERVER="192.168.1.100" \
  -e SYSLOG_PORT="514" \
  -e NODE_ID="agent-sw01" \
  -e NODE_LABEL="Switch-01 (1F)" \
  ninja-agent
```

ホストネットワークを使用すると、コンテナはホストのネットワークインターフェースで見える通信を監視できます。

専用の macvlan ネットワークを使う環境では、`--network=host` を `--network=<macvlan-network-name>` に置き換えてください。

適切なネットワーク設定は、ホストのプラットフォームとネットワーク設計によって異なります。

## 環境変数

| 変数            | 必須   | 説明                                             | 例                          |
| --------------- | ------ | ------------------------------------------------ | --------------------------- |
| `MANAGER_URL`   | はい   | Network-NINJA Manager の URL                     | `http://192.168.1.100:8080` |
| `SYSLOG_SERVER` | はい   | Syslog 送信先の IP アドレス                      | `192.168.1.100`             |
| `SYSLOG_PORT`   | いいえ | Syslog 送信先ポート(デフォルト `514`)          | `514`                       |
| `NODE_ID`       | いいえ | 一意のノード識別子(デフォルトはホスト名)       | `agent-sw01`                |
| `NODE_LABEL`    | いいえ | Manager に表示される名前                         | `Switch-01 (1F)`            |

その他の通信監視オプションは、Manager の設定から配信されます。

## Agent の動作

各 Agent は、2 つの定期的な管理処理を行います。

### ハートビート

Agent は 30 秒ごとに Manager へハートビートを送信します。Manager は最後に受信したハートビートの時刻をもとに、ノードの状態を判定します。

| 状態      | 条件                                         |
| --------- | -------------------------------------------- |
| `ONLINE`  | 最後のハートビートから 2 分以内              |
| `OFFLINE` | 最後のハートビートから 2 分以上経過          |

### 設定の問い合わせ

Agent は 60 秒ごとに Manager へ設定の更新を問い合わせます。

```
GET /api/config/<node_id>
```

設定の変更を検出すると、Agent は新しい設定で監視プロセスを再起動します。

## REST API

| メソッド | パス                   | 説明                                   |
| -------- | ---------------------- | -------------------------------------- |
| `POST`   | `/api/heartbeat`       | Agent のハートビートを受信             |
| `GET`    | `/api/nodes`           | ノード一覧を取得                       |
| `DELETE` | `/api/nodes/:id`       | ノードを削除                           |

| `GET`    | `/api/syslogs/count`   | Syslog レコードの総数を取得            |

Syslog レコード取得時のクエリパラメーターの例:

```
q=<search-text>
source=<source-address>
limit=<maximum-results>
```

## 設定の配信

Manager は複数の Agent に設定を配信できます。

```
curl -X POST http://manager:8080/api/config/deploy \
  -H "Content-Type: application/json" \
  -d '{
    "node_ids": [
      "agent-sw01",
      "agent-sw02"
    ],
    "syslog_ip": "192.168.1.200",
    "syslog_port": 514
  }'
```

配信の流れは次のとおりです。

```
1. 管理者が Manager で設定を更新
                         |
                         v
2. Manager が設定を保存
                         |
                         v
3. Agent が定期的に Manager へ問い合わせ
                         |
                         v
4. 各 Agent が設定の更新を検出
                         |
                         v
5. Agent が新しい設定で監視を再起動
```

## ネットワーク設計上の考慮事項

Network-NINJA を導入する前に、次の点を確認してください。

- 各 Active Trap Zone が正規のシステムで使われていないこと
- 自組織の環境で、内部偵察の対象としてもっともらしいレンジを選んでいること
- ルーティングの変更が本番通信を妨げないこと
- 除外が必要な監視・管理・トラブルシューティング用の通信を洗い出していること
- 各 Active Trap Zone の通信をどのセンサーが受けるかを決めていること
- 必要に応じて、戻り経路の挙動を検証していること
- ネットワーク基盤から届いた通信を Agent が観測できること
- 管理された環境でルーティングと検知をテストしていること
- 各 Active Trap Zone の目的と管理責任者を文書化していること
- ルーティング設定が組織の通常の変更管理プロセスで管理されていること

Network-NINJA は、組織のルーティング設計の妥当性を自動的に検証しません。設計が安全かつ環境に適しているかを確認する責任は、ネットワーク管理者にあります。

---

## セキュリティ上の考慮事項

Network-NINJA はネットワーク通信を観測し、送信元アドレス、宛先アドレス、ポート、タイムスタンプなどのイベント情報を保存する場合があります。

そのため、導入時には次の点を考慮してください。

- Manager へのアクセス制御
- Web UI と REST API の保護
- Syslog 転送経路の保護
- データベースファイルの権限
- ログの保存期間に関する要件
- プライバシーおよび組織のポリシー
- ネットワーク設定の変更管理
- 管理用通信と監視対象通信の分離
- コンテナ権限の妥当性確認
- 認可された管理者へのアクセス制限

適切な保護なしに、Manager のインターフェースを信頼できないネットワークへ直接公開しないでください。

---

## 制約事項

Network-NINJA の検知を、システムが侵害されたことの証拠として扱わないでください。

検知イベントは、選択された通信が Network-NINJA センサーに届いたことを示すものです。考えられる原因には次のようなものがあります。

- 悪意ある偵察
- 不正アクセス
- マルウェアの活動
- 運用上のテスト
- 監視のための通信
- 利用者による試行
- ルーティングの誤り
- アプリケーションの設定誤り
- その他の正規または偶発的な通信

イベントは、エンドポイントのログ、認証記録、ファイアウォールのログ、DNS のログ、フローデータ、インシデント対応用のテレメトリーなど、他の情報と合わせて調査してください。

## ユースケース

### 内部偵察の早期検知

ICMP、HTTP/HTTPS、SMB で Active Trap Zone を探索するホストを、偵察が本格的なラテラルムーブメントに発展する前に検知します。

### 想定外のネットワークアクセスの検知

通常の通信が想定されないネットワークに向かう通信を観測します。

### 分散拠点の監視

支店、店舗、リモート拠点にすでにあるルーターやスイッチ上に、軽量な Agent を配置します。

### SMB 通信の監視

Active Trap Zone に届く TCP/445 の通信を観測します。

### セキュリティアーキテクチャの検証

ネットワークのセグメンテーションや想定した通信経路が、設計どおりに機能しているかを確認します。

### Security by Design の演習

Active Trap Zone とセンサー配置の設計を通じて、組織のトポロジーとルーティングアーキテクチャへの理解を深めます。

### 研究・教育

管理された環境で、ルーティングベースの検知面、分散センシング、ネットワークデセプションの概念を探究します。
